# 文档写入工具与 Search 实测报告

日期：2026-10-04。服务代码：`115d159`。本次只增加测试脚本和报告，未修改服务实现。

## 1. 结论

**写入套件的功能闭环已可用，批量方式明显优于逐文件写入，但性能还不适合频繁更新较大的库。Search 目前是可用的关键词检索原型，尚不是完善的语义 RAG。**

- 19 项写入行为检查全部符合预期，覆盖建目录、删除、回滚、幂等、版本冲突和撤权。
- 同样修改 28 个文件，批量替换将调用从 56 次降到 2 次、发布快照从 28 个降到 1 个。
- 约 4 MiB 的库：逐文件替换耗时 **436.52 秒**，批量替换仍需 **23.13 秒**。批量化解决了重复工作，但尚未解决单次整库处理成本。
- Search 的 4 类关键词查询都命中预期文档；同义表达和跨语言表达未命中。
- 用户指定的私人库当前未配置检索插件。只测试了其不可用状态，没有读取正文或返回片段，没有自动配置插件、建索引或修改知识文件。

| 项目 | 说明 |
|---|---|
| 环境 | Windows build 26200；Intel Core Ultra 5 135H，18 逻辑核；可见内存约 14.9 GiB |
| 软件 | Python 3.11.15、MCP SDK 1.30.0、FastAPI 0.141.1、Uvicorn 0.53.0 |

| 写入对照 | 同一新版本服务上的「逐文件 read_file/write_file」与「file_manifest/apply_changes」；不是旧版和新版代码对照 |
| 计时 | 包含客户端请求、服务鉴权、文件处理、发布与响应解析；不含建库、MCP 初始化、准备数据和事后校验 |
| 存储量 | 新增快照中文件内容的逻辑字节量，不含文件系统分配开销、SQLite、审计和索引 |
| 请求/响应大小 | SDK 应用消息的 JSON 序列化字节量；不含 HTTP/TCP 开销，不等于模型 token 数 |

本次是**脚本驱动的工具使用测试**，没有让 LLM 自主选工具，不能据此声称 Agent 自主任务成功率。也没有做百人负载、Linux 部署性能或长时间稳定性测试。

写入性能原计划每组 3 轮。发现 4 MiB 样本逐文件替换需约 7.3 分钟后，停止后续重复，保留 **9 个完整完成的案例**，中断中的案例不计入。下面主表使用完整配对的第一轮；补充表列出全部已完成样本。没有据此估计 P95/P99 或生产 SLA。

## 3. 写入效率

### 3.1 同一任务的调用与耗时

新增导入为 28 个 8 KiB 文件，带多层中文目录。小库预置 32 个 8 KiB 文件，大库预置 128 个 32 KiB 文件；两者另有初始 README。替换任务均修改其中 28 个文件，修改前后文件大小保持一致。

| 任务 | 逐文件调用 | 批量调用 | 逐文件耗时 | 批量耗时 | 本轮加速比 |
|---|---:|---:|---:|---:|---:|
| 空库导入 28 个文件 | 28 | 1 | 33.10 秒 | 1.08 秒 | 30.64 倍 |
| 约 256 KiB 库，替换 28 个文件 | 56 | 2 | 70.57 秒 | 5.70 秒 | 12.38 倍 |
| 约 4 MiB 库，替换 28 个文件 | 56 | 2 | 436.52 秒 | 23.13 秒 | 18.87 倍 |

逐文件替换每次先 read_file 取得当前版本，再 write_file。批量替换用一次 file_manifest（limit=200）取得整库版本，再 apply_changes。初始化和工具发现不计入调用数。清单超过一页时需要更多调用，不能普遍认为永远只需两次。

| 已完成样本 | 逐文件次数及范围 | 批量次数及范围 |
|---|---|---|
| 导入 28 个文件 | 2 次：32.26–33.10 秒 | 2 次：1.08–1.11 秒 |
| 256 KiB 库替换 | 1 次：70.57 秒 | 2 次：4.42–5.70 秒 |
| 4 MiB 库替换 | 1 次：436.52 秒 | 1 次：23.13 秒 |

### 3.2 发布与存储

| 任务 | 逐文件新增快照 | 批量新增快照 | 逐文件新增内容量 | 批量新增内容量 |
|---|---:|---:|---:|---:|
| 导入 28 个文件 | 28 | 1 | 3.172 MiB | 0.219 MiB |
| 256 KiB 库替换 | 28 | 1 | 7.000 MiB | 0.250 MiB |
| 4 MiB 库替换 | 28 | 1 | 112.000 MiB | 4.000 MiB |

复制函数计数、目录中的新增快照数、SQLite 新增发布回执数一致。每个完整案例均检查最终 28 个目标文件与预期内容一致，文件总数正确。

当前 apply_changes **仍然复制整个库**，只是把一组修改合为一次。不能将这次优化描述为「按修改量增量存储」。历史清理可以控制长期占用，但不能降低一次发布的复制与校验成本。

### 3.3 返回给 Agent 的数据量

| 替换任务 | 逐文件响应合计 | 批量响应合计 | 减少 |
|---|---:|---:|---:|
| 256 KiB 库 | 1,117,944 字节 | 28,022 字节 | 97.49% |
| 4 MiB 库 | 1,118,056 字节 | 77,910 字节 | 93.03% |

取得版本时，read_file 会同时返回默认分页的正文及行信息；file_manifest 只返回元数据。这避免了为了版本号把许多正文送回 Agent。表内使用 SDK 完整返回对象序列化，可能同时包含文本与结构化内容；不同 Agent 的上下文注入方式不同，因此不直接换算 token 节省。

## 4. 正确性与操作体验

**19 项预期行为全部通过。** 其中既有成功操作，也有预期应被拒绝的请求，不能把它理解成 19 次请求都成功写入。

| 检查组 | 实测结果 |
|---|---|
| 目录 | 自动创建多层父目录、单独 mkdir、删除空目录均成功 |
| 删除 | 文件删除需版本；非空目录未带 recursive 时拒绝，携带整库版本与 recursive 后成功 |
| 失败回滚 | 先创建新文件、再故意创建同名已有文件：整批拒绝，活动指针、快照量和回执量不变 |
| 重试 | 同一 request_id、相同请求返回原回执，不新增快照；换内容则 request_conflict |
| 冲突 | 旧整库版本、旧文件版本均被拒绝 |
| 错误提示 | 缺父目录为 parent_not_found；父路径为文件为 parent_not_directory |
| 输入边界 | 中文 request_id、超过 100 项、上跳路径和不支持的扩展名均被拒绝 |
| 动态授权 | 撤销直接写权限后，重复原成功请求也被拒绝 |

另做了 5 个同时基于同一整库版本的写入：**1 个成功、4 个版本冲突，只新增 1 个快照**。这是并发冲突保护测试，不是并发吞吐量测试。

### 需要明确的使用约定

1. **多个文件不要先统一 read，再逐个 write。** 实测修改无关文件后，未修改 README 的文件版本也改变，持旧版本替换被拒绝。原因是复制快照改变了文件元数据。多文件修改应走整库版本 + 批量提交；逐文件操作必须每次重新取版本。
2. **清单有分页。** 128 个预置文件、README 和 5 个目录共 134 条，默认 limit=100，需要两页；分页须带 expected_library_version。
3. **建目录和删除入口不直观。** 功能已经通过测试，但目前要在 apply_changes 的 changes 内声明操作。该命名不像 mkdir/delete_file 那样一眼可见。这是接口可发现性的判断，本次没有测 LLM 选工具准确率。
4. **工具数量与描述有成本。** 此次只开读取的 Key 暴露 5 个工具；打开直接写入后是 8 个，新增三个工具的完整 schema 与描述合计 4,951 字节。合成检索库同时打开 grep/search/direct 时为 10 个工具。不是所有 Key 固定暴露同一组工具。

## 5. Search 测试

### 5.1 私人库：只验证当前可用状态

用户指定库的状态为 `unconfigured / index_not_configured`。创建了仅授权该库、无写入权限、1 小时到期的临时测试 Key；尝试授予 Search 后：

- MCP 工具发现未提供 search。
- 5 次 REST 探测均为 HTTP 403 / capability_forbidden。
- 3 次 MCP 显式调用均返回 capability_forbidden。
- 没有返回文档内容，测试结束后临时 Key 已撤销。

未调用私人库的 read_file、grep、glob 或 list_directory；未绑定插件、构建索引或改动文档。记录只保留状态、次数、耗时、命中数及撤销结果，去除了私人库名称、ID、路径和片段。**这些被拒绝请求的耗时不能当作 Search 的检索性能。**

这也说明：配置中勾选 Search 不等于它已经可用。界面需要明确区分「未绑定插件」「未建索引」「索引失效」「可检索」。

### 5.2 隔离合成库：正常检索与表达能力

使用仓库现有 simple-rag 1.0.0，原生 SQLite FTS5/BM25，没有调用外部模型。两个库各加入 3 篇已知答案文档，其余为可控背景文本。

| 数据规模 | 索引文件数 | 片段数 | 构建耗时 |
|---|---:|---:|---:|
| 约 256 KiB，加少量答案文档 | 36 | 228 | 1.50 秒 |
| 约 4 MiB，加少量答案文档 | 132 | 3,588 | 15.29 秒 |

每个库测试 7 类查询，每类重复 3 次，共 42 次正常查询。下表耗时为各查询 3 次的中位数。

| 查询 | 预期用途 | 两库命中表现 | 小库耗时 | 大库耗时 |
|---|---|---|---:|---:|
| 访问密钥 | 中文关键词 | 预期文档排第一 | 0.670 秒 | 3.730 秒 |
| rollback | 英文关键词 | 预期文档排第一 | 1.201 秒 | 3.788 秒 |
| 模型配置 | 中文关键词 | 预期文档排第一 | 1.196 秒 | 3.895 秒 |
| 如何生成访问密钥 | 包含关键词的问句 | 预期文档排第一 | 1.349 秒 | 3.001 秒 |
| 凭证 | 希望召回访问密钥文档 | 无命中 | 1.256 秒 | 1.736 秒 |
| 回退版本 | 希望召回英文 rollback 文档 | 无命中 | 1.272 秒 | 1.676 秒 |
| 随机不存在词串 | 验证无结果行为 | 无命中，符合预期 | 1.244 秒 | 1.711 秒 |

4 类词汇相关查询在两种规模、三次重复中共 **24/24 次首条命中预期文档**；命中片段与引用行范围均经过源文比对。同义和跨语言两类共 **12/12 次无命中**；随机不存在词串共 **6/6 次为空**。

这里仅有 4 类正向关键词问题，不能把 24/24 解读为真实业务问答准确率 100%。重复调用只验证重复行为，不能扩充独立问题的样本量。

### 5.3 更新后的检索闭环

在两种规模上都验证了：

```text
绑定插件但未建索引 → index_missing
构建索引          → 能检索
通过 write_file 新增文件 → index_stale
重新构建索引      → 检索恢复
```

无有效字符的查询被 invalid_search 拒绝。正常库的工具列表中 grep 与 search 可以共存。

目前文档写入不会自动重建索引，Agent 单靠这套写入工具不能完成「修改后立即 Search」的闭环，需要管理端重建。首次配置也不是发放一个 Search 权限就够了。

检索性能还有一个明确的代码层面成本：每次查询都会通过 `Retrieval.snapshot(..., read=False)` 遍历文件并读取内容计算指纹；read=False 只是不解码返回全文，**不是不读磁盘**。命中文件还会再次校验内容。因此查询耗时不只是 SQLite 索引查询。该机制能够检测外部文件变化，但需要优化。本次未做分项 profiler，不能断言某一环节占总耗时的具体比例。

## 6. 改进顺序

| 优先级 | 建议 | 本次依据 |
|---|---|---|
| 高 | 降低发布对整库复制、全库扫描的依赖；为慢批次提供可查询的任务状态 | 4 MiB 批量修改仍需 23.13 秒，逐文件修改需 436.52 秒 |
| 高 | 以稳定的文件内容版本或逻辑版本保护单文件修改 | 无关文件发布也使旧文件版本失效 |
| 高 | 写入后自动排队更新索引，展示可检索状态；未配置插件时明确提示 | 写入后必经 index_stale；私人库当前完全不能 Search |
| 中 | 检索采用发布版本或增量变更检测，保留失效校验但减少每次全库读取 | 大库有效命中约 3–4 秒，空查询结果仍需约 1.71 秒 |
| 中 | 明确建目录、删除的入口；是否增加独立工具由接口取舍决定，底层复用同一事务实现 | apply_changes 能完成操作，但名称不直接体现这些基本能力 |
| 后续 | 用独立问题集评估向量/混合检索及查询改写 | 同义、跨语言例子未命中，当前只验证了少量关键词问题 |

建议现阶段使用方式：**小型知识库、多文件修改优先批量；Search 用于关键词证据检索；索引状态必须在使用流程中显式处理。** 尚不能将平台定位为高频写入、高并发或完善语义检索的生产系统。
