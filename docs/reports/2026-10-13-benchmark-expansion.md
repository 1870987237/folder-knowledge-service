# Benchmark 扩展进展与实测结果

本轮按“失败复核 → 独立检索指标 → 平台业务任务 → 并发负载”推进。四项均已实现并实际运行。现在可以同时判断任务是否完成、单次检索能找回多少证据，以及并发下接口是否稳定；三类指标分开报告。

## 1. 目前怎样测

以 OMP 18.2.5 + GLM-5.3-Flash 为被测通用 Agent。测试器提供自然语言业务目标和独立知识库，Agent 自主决定调用顺序。适配层只转发平台实际 MCP 工具与 instructions，不替 Agent 规划，也不暴露标准答案或本地 Shell/文件旁路。

每个基础任务、配置及重复次数重新建库、Key 和会话；任务结束后独立检查事实、来源、文件内容和无关改动。grep / search / hybrid 三组固定模型、语料和预算并轮换顺序，失败与超时保留在分母。记录逐次工具参数、返回、错误、耗时、Token 和最终答复。

平台业务测试保留阶段依赖，但不同任务使用新 Agent 会话；配置资源、重建索引、审核与启动 worker 属于独立平台角色操作，不算 Agent 工具调用。固定查询测试不用模型；并发测试使用真实 HTTP 服务子进程，与 Agent 测试分开运行。

所有库和端口均隔离。没有读取私人知识库，也没有修改日常 8791 服务。

## 2. 原基线复核

10 月 12 日冻结基线完成 108 次合成读写、180 次公开问答。此次统一离线重评分 108 次读写，仍为目标达成 **101/108（93.5%）**、严格通过 **97/108（89.8%）**；工具成功 **292/303（96.4%）**。

此前 6 个“虚报完成”实际是正确修改后多出段落空行，现归为格式差异，仍不通过精确文件验收，不抬高原成绩。另有不合法 JSON、正确拒绝却填 completed=true 等协议问题。虚报标签修正为 0，不等于完成了所有幻觉检查。

公开问答的答案判分为 171 正确、3 错误、6 未判。当前判分虽使用独立无工具会话，仍与被测模型同型号，3 个错例尚需独立模型或人工复核。详见 [失败复核](2026-10-13-benchmark-review.md)。

## 3. 单次 Search 的质量

新增固定查询 CSV、文档相关性标签及独立 runner。每个查询只调用一次真实 MCP Search，最多返回 10 个片段，按首次出现顺序去重成文档，计算文档级 Recall@K、nDCG@K、MRR 和 Precision。

8 项合成查询在内置 simple-rag 与独立程序 simple-rag-python 各运行一次，均 8/8 调用成功，正例查询 Recall@3 为 100%，无答案查询 1/1 返回空。规模太小，仅用于检查评测与插件接入。

进一步对已有 20 道 BrowseComp-Plus 题、304 篇文档运行固定查询。查询取原 Search 组第 1 轮的首次 Search，要求此前未读取/检索正文；不按成功与否挑选，不依据答案改写，不截断长问题。全部 20 题符合条件，查询及证据标签指纹已冻结。

| K | Recall@K | nDCG@K | MRR@K | Precision@K |
|---|---:|---:|---:|---:|
| 1 | 14.5% | 0.600 | 0.600 | 60.0% |
| 3 | 23.2% | 0.398 | 0.692 | 33.3% |
| 5 | 27.1% | 0.363 | 0.692 | 25.0% |
| 10 | **31.3%** | **0.361** | **0.700** | **14.5%** |

本次使用 simple-rag-python（Markdown 分块 + SQLite FTS5/BM25，非向量索引）。20/20 调用成功，1 次空结果；索引构建 5.12 秒，查询耗时中位数 4.26 秒、P95 5.22 秒。该查询耗时包括平台校验、程序执行及 MCP 往返，不是纯数据库查询时间。

**解释：**首次查询往往只拿到一部分证据，Agent 因而需要改写查询和补读。原 Search 组多轮探索的累计证据召回是 71.3%，与这里单次 31.3% 的口径不同。二者差距支持继续分析查询策略与证据补充，不能单独证明重复搜索都是无效调用。10 个片段也可能来自同一文档，返回预算会限制文档覆盖。

这些是缩小语料、固定 Agent 生成查询的内部指标，不能称为官方完整榜单成绩。检索算法与索引组织仍由插件负责；平台负责统一接口、权限和结果契约，评测器负责固定输入和核验输出。

## 4. 平台业务闭环

新增六个自然语言任务：

| 任务 | 独立验收 |
|---|---|
| 多库读写 | 查询只读团队库，把事实写入个人库，其他文件不变 |
| 未授权拒绝 | 不泄露隔离库内容；测试器额外按库 ID 探测，确认被拒绝 |
| 修改后索引过期 | 文档准确修改，旧索引明确返回 index_stale |
| 重建后读取 | 手动重建后，新会话查到新值和真实来源 |
| 提交材料 | 材料进入 pending 收件箱，正式库尚未改变 |
| 审核发布后读取 | 组织管理员审核、worker 发布后，新会话读到新增事实；回执 completed |

更新链路使用 reference-docs@0.2.0 确定性测试模板，验证模板绑定、任务状态、人工审核边界及回执，不评判记忆整理大模型质量。审核账号不会交给 Agent。

首个完整试跑六个任务均通过，共 14 次 Agent 工具调用、1 次错误后恢复；平台角色操作单独记录 18 项。早期接入试跑曾因测试器错误假定注册返回登录 token 而中止，原记录保留，已改为真实注册—激活—登录流程。另一次合法拒绝却报 completed=true，现将完成目标和协议通过分别记录。

后续加严引用验收：答对值还必须引用实际工具返回过正文且包含目标事实的文件；保存每个任务前后的合成库快照及指纹，便于复核无关改动。本轮为接入与流程验证，尚未把新增任务按多个模型、插件各重复三次。

加严后的复测以提交 `12114f6` 执行，**目标达成 6/6、严格通过 6/6，工具成功 15/16**；一次错误为创建文件时未创建父目录，平台返回 parent_not_found，Agent 随后恢复。每项任务耗时分别为 51.56、17.69、39.70、22.23、26.88、25.17 秒，总计约 183 秒（不含平台配置和审核操作）。两个完整试跑分别保留，不能把修复前中断记录丢弃后宣称稳定通过率 100%。

## 5. 并发负载

Windows 本机回环，客户端和 HTTP 服务不同进程；使用当前默认并发上限 32、32 个约 4 KiB 合成文件。每客户端连续发 3 个请求、无思考时间、不自动重试。初测 6 个并发档位 × 4 类负载，共 2,292 请求；不是相同人数的日常在线使用。

以下只读和 Search 来自初测；混合与后台来自补验，补验开始时明确观察到 worker 为 running。补验 4 档 × 2 类共 816 请求，避免把后台尚未启动误当成并行负载。两轮不合成一个通过率。

| 场景 | 10 客户端成功/请求 | 25 客户端成功/请求 | 100 客户端成功/请求 | 25 客户端成功请求 P95 |
|---|---:|---:|---:|---:|
| 只读 | 30/30 | 75/75 | 22/300 | 0.95 秒 |
| Search | 30/30 | 75/75 | 5/300 | 11.80 秒 |
| 混合读写（约 20% 创建） | 28/30 | 38/75 | 9/300 | 5.49 秒 |
| 后台生成候选 + 读取 | 30/30 | 75/75 | 0/300 | 0.91 秒 |

- 高并发有大量 HTTP 503，与当前服务并发/连接上限相关；100 个客户端同时起跑会触发突发拒绝，不能把失败请求的快速返回当成低延迟。
- 混合场景已出现 SQLite state_busy。10 客户端时 2 个失败均为读取；25 客户端时 32 个读取、5 个写入失败，说明同库写入竞争也影响读取。
- 100 客户端混合场景另有 35 次客户端 ReadError，应单列为传输失败，不能说都是数据库锁错误。
- 补验中已确认成功的写入回复与最终新文件数量一致（1、6、10、4 个），未观察到成功回复对应文件丢失。未覆盖同路径竞争覆盖或长时间故障恢复。
- 四档后台任务均从 running 开始，最终各 3 个任务到达 candidate_ready；未自动审核发布。

**结论：目前不能承诺百人持续并发。** 已具备可复现负载入口，优先处理状态库竞争与请求排队/背压，再测容量。不能只把并发上限调大就宣布解决。这里每档请求少、同机短时运行，缺少独占硬件、长时间稳定性和业务 SLA，当前数字用于定位瓶颈。

下一轮建议按优先级：

1. 修复并发测试暴露的 state_busy 和突发拒绝，定义目标并发、持续时间及成功率/P95 门槛，再运行容量验收。
2. 固定本轮查询和任务，对新的索引插件开展对照；同时观察检索分数与 Agent 成功率、调用数是否一致改善。
3. 新业务任务扩展到三次重复及部门/用户组继承、撤销授权、同路径并发修改、更新失败恢复。
4. 用独立模型或人工复核公开问答边界样本，再逐步扩大语料与问题规模。

不需要先做看板才能测；先稳定输入、判分口径和回归结果，再将这些报告接入管理台。

本轮修改相关的基础 Agent、数据集、公开基准、检索、业务流程及负载测试共 65 项通过；diff 检查通过。没有变更生产服务代码或 UI。
