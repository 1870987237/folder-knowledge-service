# 通用知识库插件：真实模型整理质量测试

结论：当前版本能正确处理常见增量整理，也能保留人工改动，但尚不能视为稳定的无人审核整理器。36 次样本中，33 次产出有效候选；31 次事实、归位和处理理由符合标准，2 次安全待审但理由有误，3 次被协议校验拒绝。另有 2 次人工编辑场景出现排版瑕疵。

本次保留全部成功与失败，不修改插件后重新挑选结果。适合继续采用“生成候选、人工审核后发布”。

## 方法与口径

- 对象：`general-knowledge@1.1.0`，冻结当前 `program.py`；SHA-256 为 `ab817e0d56c35e4c653d60324c2aea39ad219ced7742b7060e0d93e2f58f2988`。
- 模型：现有配置的 `hyper-op/GLM-5.3-Flash`，temperature 0.1；真实上游调用，未模拟整理决策。
- 18 个场景，每个独立重复 2 次。基础集 14 个，补充挑战集 4 个；每个批次的输入和预期均在调用前固定。两个样本并行执行，不是压力测试。
- 基础库包含 Atlas API、Atlas 备份、Boreal API 三篇确定事实；挑战集增加 Atlas 预发布 API。每个样本从独立副本开始，人工新增场景另加一篇文档。
- 通过标准文件协议准备快照，由真实插件子进程处理，再验证候选。初始化和种子库是确定性构造；实际被评测的整理启用 `llm` 模式。成功候选再重放同一材料检查幂等性。
- 不访问生产知识库、不发布候选，不测试网页、MCP 工具选择、BM25 检索或并发服务能力。这些结果不能代替整个平台端到端验收。
- 当前助手逐项对照预先写明的标准，检查实际 Markdown 正文、处理动作、理由和模型响应；另用程序检查输入不变、重放一致及关键隔离/事实约束。不是人类专家盲评，也未用 Flash 自评。

“通过”要求产出有效候选且事实、目标、适用条件和理由正确；“部分通过”表示安全处理但解释不准确；“失败”表示未产出有效候选。排版问题单独记录，不混入事实正确率。

## 实际整理示例

### 局部纠错保留其他事实

原文：

> Atlas生产API请求超时为30秒，最多重试2次，只允许HTTPS连接。

提交“只将超时改为 45 秒，其他不变”，两次候选正文均为：

> Atlas生产API请求超时为45秒，最多重试2次，只允许HTTPS连接。

### 混合材料拆开处理

提交“重试间隔是 5 秒；超时是 90 秒”。两次都生成 `merge + defer`：5 秒进入 API 文档，90 秒作为冲突待审。没有因其中一项可接受，就把整段全部写入。

### 杂乱会议记录提炼

输入同时包含已通过规定、被否决建议、猜测和临时待办。两次都只新增：

- API 文档：只有幂等请求可以自动重试。
- 备份文档：每月第一个工作日进行恢复演练。

原 30 秒超时、2 次重试、HTTPS、每日 02:00 备份与保留 7 天均保留；“所有请求都重试”“保留 30 天”等未通过建议没有被写成生效规定。

## 发现的问题与建议顺序

### 1. skip 的提示与校验不一致

系统提示表示 `skip` 可无证据，但字段校验仍要求存在 `evidence`。两次模型都返回正确的 skip 判断，却省略该字段，导致整次失败。

建议先统一契约：明确输出 `evidence: []`，并仅对合法 skip 的缺省证据做兼容处理。不能放宽 create/merge/revise 的证据要求。

### 2. 证据来源错误没有纠正机会

同义去重的一次响应同时引用当前材料和旧文档。语义判断正确，但旧文档句子不属于当前材料，校验阻止候选。这个拦截是正确的，属于交付可靠性缺口。

建议进一步明确两个来源的区别；遇到 schema/引文错误时，可提供一次有边界的纠正机会，要求模型修正输出。保留原失败与重试记录，不删除不合规引文后直接放行。

### 3. 模型会误判兼容性，审核理由也需要看

未经自标注的指令干扰样本中，模型安全地整体待审，但两次都认为 TLS 1.3 与 HTTPS 存在冲突。这不是成立的冲突判断：TLS 版本限制可以补充 HTTPS 连接要求。

可因来源可疑而待审，但不能用错误的协议关系作为依据。因此这两次记“部分通过”，而非完整质量通过。四个指令样本也不足以证明抗提示注入能力。

### 4. 手动追加正文后出现重复页脚

人工在原文末尾追加幂等限制后，原“适用范围：Atlas”进入正文；插件渲染又增加一份页脚。两次生成的 Markdown 都有两处适用范围。事实没有丢失，但排版不够整洁。

建议将展示元数据与可编辑正文分清，不依赖“页脚恰好位于最后一行”来识别生成内容。

### 5. 困难材料存在长尾耗时

3 次上游尝试在本测试转发器的 43 秒超时后失败，插件内置重试均恢复。插件本身请求超时为 45 秒；该转发器可能比直接生产调用更早结束请求，因此不能将本次超时率直接套用生产。

保留失败信息与重试状态，允许用户识别“模型等待”与“处理失败”。本次没有调整超时、提示词或插件代码来提高结果。
