# 知识平台 Agent Benchmark：首轮结果

已建立可重复运行的任务级评测：给 OMP 自然语言任务，让它自行使用知识平台，最后独立检查答案和文件结果。

## 做了什么

- 使用已配置的 **GLM-5.3-Flash + OMP 18.2.5**。
- 构造 **24 篇独立合成文档**，未访问私人知识库。
- **12 个任务 × 3 种工具配置 = 36 次执行**：覆盖查找、跨文档综合、旧版本辨别、无答案拒绝，以及创建、修改、多文件更新、删除、移动和权限拒绝。
- 每次重置文档与会话，不提供答案或工具调用步骤；保存模型事件、实际 MCP 调用、耗时和最终文件。

## 核心结果

| 配置 | 实际目标达成 | 工具调用成功率 | 写入任务耗时中位数 | 三文件更新总耗时 |
|---|---:|---:|---:|---:|
| grep | 12/12 | 47/48，97.9% | 13.49 秒 | 20.75 秒 |
| Search | 12/12 | 37/38，97.4% | 12.21 秒 | 17.07 秒 |
| 两者同时开放 | 12/12 | 38/40，95.0% | 13.30 秒 | 17.52 秒 |

**126 次工具调用，122 次成功，合计 96.8%。**4 次错误均自行恢复；没有发现实际虚报修改或无关文件改动，只读 Key 场景均正确拒绝写入。

另有 **1 次返回状态不一致**：Agent 正确回答“资料不足，无法确定”，但填了 `completed=true`。所以实际目标达成是 **36/36**，包含状态协议的严格通过是 **35/36**。这不是编造奖金金额。

## 工具有没有让 Agent 走弯路

- **3 次不存在文件错误**：新建前先检查目标文件，是合理探测，不能直接算成误导。
- **1 次遗漏版本参数**：修改文件时没传 `expected_version`，收到明确提示后补齐，修改成功。可以继续改善条件必填参数的可发现性。
- **批量能力被主动使用**：三个配置的 Agent 都自行选择一次批量变更完成三个文件更新；任务没有告诉它用哪个工具。每次只产生 **1 次发布**。

单次写工具的服务端耗时中位数约 **2.8 秒**；表中的 12–21 秒还包含模型思考、查资料、核实版本和答复。两者是不同指标，不能把整个任务耗时当成接口延迟。

## Search 结果怎么理解

当前 Search 使用 **SQLite FTS5 / BM25 全文索引**，还不是向量检索。

- Search 组 6 个问答任务均用过 Search，全部获得正确结果。整个任务集调用 **38 次**，grep 组 **48 次**。
- 跨文档问题中，一次 Search 就能拿到负责人、维护窗口、备份及阈值的证据；不是只测“接口是否返回成功”。
- Search 也有低效情况：查一个资料不存在的问题时用了 **12 次调用、17.20 秒**；grep 组用 **4 次、9.25 秒**。需要改进证据不足时的停止判断。
- 本轮累计模型输入分别为 **27.6 万 / 19.0 万 / 20.7 万 tokens**（grep / Search / 混合）。这是会话各次请求的累计输入，不是文档体积。

**当前只能确认基本工具链可用，不能据此宣布哪种检索方式普遍更好。**每个任务每种配置仅运行一次，库也较小；混合配置能否更好取决于 Agent 是否选对工具。

### 测量说明

OMP 原生 MCP 自动发现曾出现工具目录已返回但工具未注册的接入异常。正式 36 次统一使用薄适配层，将服务端原始 schema 注册为 OMP 工具，调用仍通过真实 MCP HTTP；任务决策仍由 OMP 完成。本报告不代表原生 MCP 客户端的兼容性结论。

正式轮次的 36 次记录全部保留，没有重跑替换任务。评分器将“正确拒绝但完成标志写错”从实际虚报中分离，对全部已保存证据统一离线重评分；原评分仍在结果中。任务目标和 Agent 提示没有变化。
