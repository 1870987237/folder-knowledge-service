# Worker 与知识库配置边界

## 目标

组件职责清晰，复用已有任务队列和权限逻辑。不增加第二套调度系统，本次不做自动构建索引。

## 已确认的边界

- HTTP、Git 同步、知识更新保持独立进程。
- 提供统一启动入口，管理台查看心跳、任务数量、失败原因并重试。不从网页启停进程。
- 组织库配置权来自组织管理员身份；创建者身份、库成员授权、部门/用户组授权不能单独赋予组织库配置权。
- 个人私有库由本人管理，不因加入组织而向组织管理员开放。

## Worker 实现

| 组件 | 负责 | 不负责 |
|---|---|---|
| `service.py` | 本机统一启动和结束三个子进程，分组件日志；子进程退出则整体退出并报错 | 不处理业务任务，不重试任务，不自动批准插件执行 |
| `worker_runtime.py` | 共用进程锁与心跳格式解析，独立心跳维护 | 不读取业务材料，不解释任务结果 |
| `git_worker.py` | Git 队列、拉取、验证和发布 | 不调度知识更新 |
| `template_worker.py` | 更新队列、程序执行、候选与审批发布 | 不管理 Git 任务或服务进程 |
| `workers.py` | 聚合现有心跳、任务计数和最近失败 | 不创建第二套任务表、不启动子进程 |

统一入口：`python -m folder_kb.service --host 127.0.0.1 --port 8791`。
必需配置为 `KB_ROOT`、`KB_STATE_DIR` 和 `KB_ADMIN_TOKEN`。程序先初始化状态库，检查端口及现有 worker 锁，再启动三个模块。发现旧实例时拒绝启动，不接管或终止旧实例。

本机启动器不提供静默自动重启；意外退出会停止其他子进程并返回失败，由运行人员检查日志后重启。Docker 部署继续由 Compose 管理各进程并使用其重启策略，不在容器里再套一层本机启动器。

日志位于 `KB_STATE_DIR/service-logs/{http,git,updates}.log`。启动器仅向 HTTP 传管理员令牌、向 Git worker 传 Git 配置、向更新 worker 传显式白名单中的模型凭据。开启更新程序执行仍需 `KB_TEMPLATE_TRUSTED_PYTHON=1` 及已有审批配置；启动进程不代表自动信任程序包。

`GET /admin/api/workers` 只对平台管理员开放，按组件返回在线状态、最近心跳、排队数、执行中数、待审核数、历史失败数及最近 5 条失败。30 秒内有有效心跳才显示在线，心跳表示存活，不代表任务取得进展。查询不读取文档或收件箱正文。

重试复用现有接口：Git 为 `POST /admin/api/repositories/{id}/sync`，更新为 `POST /admin/api/update-jobs/{id}/retry`。Git 按当前配置重新同步，更新任务沿用既有材料与权限校验；历史失败记录保留，重试不等于审批发布。

## 知识库配置（第一阶段已实现）

配置权使用独立的 `can_configure_library` 判断，并由 `check_configuration` 统一校验。个人所有者和所属组织管理员可以配置；库级 `manager`、部门和用户组授权仅保留内容角色能力，不再授予组织库配置权。超级管理员保留平台维护能力。

建议分成平台资源配置与知识库实例配置：

| 配置 | 个人所有者 / 所属组织管理员 | 超级管理员 |
|---|---|---|
| 库名称、用途 | 可配置自己的库 | 平台维护 |
| 组织成员、部门、用户组对库的授权 | 仅所属组织管理员 | 平台维护 |
| Agent 接入方式、提交及直接写入开关 | 在库能力边界内配置 | 平台维护 |
| 索引状态、构建、测试 | 对已绑定且批准的插件操作 | 平台维护 |
| 选择插件版本、模型连接及更新参数 | 仅选择平台明确授权的资源 | 安装、审核及授予可用范围 |
| 上传/执行程序、服务器目录、Git 凭据、模型密钥 | 不直接操作 | 管理底层资源 |

个人 Key 仍由个人管理，不能因为管理知识库而获得其他人的完整 Key 或修改其其他库权限。库管理员管理的是库允许的能力和授权范围。组织共享 Key 的归属和生命周期需另外明确。

用户工作区的库内顶部提供“知识库设置”，包含基本信息、模板与更新、Agent 接入、检索索引四个标签；组织管理员另有成员权限入口。库列表返回 `can_configure` 控制入口，接口逐次重新校验，因此降权后即使页面尚未刷新，也不能继续操作。内容读取、编辑和发布继续使用既有角色。`/admin/api/` 仍只接受平台管理员凭据。

新增接口（均在 `/portal/api/libraries/{id}` 下）：

- `PUT /settings`：仅修改名称，拒绝额外字段，写审计记录。
- `GET /index`：查看已绑定检索插件的索引状态。
- `POST /index/build`：显式构建或重建；沿用平台既有插件执行审批与索引发布逻辑。
- `GET /index/search`：测试索引检索，保留原 `/search` 的正文 grep 行为。

成员授权、部门/用户组授权、共享范围和 Agent 接入接口统一使用配置权检查。个人 Key 仍由 Key 所有者管理。插件/模型资源授权、模板选择、人员材料提交与库内更新任务已补齐，见 [模板与增量更新管理](library-template-workflow.md)。索引仍需手动构建。
